# HY04: DTR die-temperature readout

This ULX3S/LFE5U-85F experiment now has three complete board loads in
`observations.log`, with the exact `hy04.v` and `hy04.config` that ran.
The designs were built with the commands below and the records collected
with `run.py hy04.bit Y4 3 90 --settle-seconds 2`. Emulator implementation
used those artifacts without another hardware run. DTR now executes in the
event kernel and fast mode with the measured environment profile and explicit
limits below.

## Reading

The reproducible comparison is [analysis.txt](analysis.txt), generated by:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 hy04_analyse.py observations.log --board-reading > analysis.txt
```

Each load has 730 unique windows and 731 identical startup replays, with an
initial byte of **0x9E** and no startup-window transition. All final-window
codes are 0x9E. Each of the three drift runs has 601 samples spanning
60.000048 s; min/max/median are 0x9E, spread and code/minute slope are zero.
This is no *observed code drift*, not a measurement of constant die temperature.

There are 1995 isolated conversions: 48 each of kinds 1–4, plus 1803 kind-9
readings. The normal value order is `00, 01, 02, ... 1E, 9E`. Raw sequences
are not identical: 173 one-tick dwell codes appear, for example `03,07,04`
or `1B,1F,1C`. Retaining all those samples is essential. As an explicit skew
hypothesis, removing only one-tick dwell values gives exactly `00..1E,9E`
in **1995/1995** isolated windows. The persistent increments take 24 or 25
observer ticks (0.96 or 1.00 us), and their offsets also vary. No fixed
values-and-timestamps sequence fits every conversion.

This is a visible ascending binary count, not a conventional successive-
approximation sequence of MSB-to-LSB trial bits. A hidden successive-
approximation circuit is neither demonstrated nor excluded by these pins.
The one-tick values are consistent with asynchronous bit skew/synchronization,
but their physical duration and internal cause cannot be resolved here.

The first `00` is always seen at rise + 3 observer ticks. That is the reset/
start response, **not** conversion completion. The 100 us and 600 us high
pulses hold `00` throughout the high interval; counting becomes visible only
after deassertion. There is no repeated valid result while held high.

One tick is 40 ns. The final columns subtract the nominal 2.5-tick observer
pipeline delay, with nominal +/-0.5-tick sampling uncertainty plus unknown
routing/metastability delay. `analysis.txt` gives persistent-code timing ranges
and medians relative to both rise and fall, as well as every raw value-sequence
variant and the one-tick events. Long and short widths have different latency
distributions; the documentation's 70 us diagram is not this board's measured
delay.

Retrigger observations, 48 windows per kind:

- Kind 5, 10 us spacing: both rises reset to `00` at +3 ticks, and only the
  restarted sequence reaches 9E. Final latency after the last fall is
  810 / 823 / 834 ticks (min / median / max).
- Kind 6, 30 us: both resets are visible; the old partial count is abandoned.
  One final 9E, at 810 / 820.5 / 833 ticks after the last fall.
- Kind 7, 60 us: the first conversion already completes before the second
  rise. Both independent conversions reach 9E; this is not a busy retrigger
  at the actual approximately 32 us conversion time. Last-fall latency is
  810 / 821 / 834 ticks.
- Kind 8, eight starts 20 us apart: all eight resets are visible. Only the
  last sequence completes, at 812 / 821 / 834 ticks after its fall. No queued
  sequence appears in the following 800 us observation tail.

These visible resets and abandoned counts support **restart**, rather than
ignore or a serialized queue. Identical final codes alone would not establish
that; the intermediate progress/reset observations do.

The steps are regular **after startup**, but not uniformly spaced **from
fall** within one or two cycles. Pooled persistent step offsets are tabulated
in `analysis.txt` (min/median/max and max-minus-min spread, in 40 ns ticks).
For 01 they are **27/88/101**, spread **74 ticks**; for 1E they are
**748/809/823**, spread **75 ticks**. Even the one-tick pulse class starts 01
at 76/88/101 ticks, versus a 24/25-tick subsequent period. Correcting the
observer pipeline subtracts 2.5 ticks from offsets without changing spreads.
All **173/173** one-tick values immediately precede an adjacent persistent
increment (`n`, transient, `n+1`), and every transient contains only old/new
bit mixtures. They sit at count boundaries, consistent with bus skew of one
increment, not additional conversion steps; the pins do not prove the cause.

The event kernel and fast mode select the **two-valued fallback**:
00 while high and throughout conversion, then the profile byte at latest fall +
**32.740 us**.
Bit 7 remains clear until done. This is the pooled isolated fall-to-final
median of 821 observer ticks corrected by 2.5 ticks, weighted toward the 1803
one-tick drift readings. The deterministic completion policy does not replay
width/phase dependence. Assertion clears immediately; no invented sub-tick
response delay or low-bit count is added.

Still open: no Celsius scale; one chip at one uncontrolled room temperature;
other codes and temperatures; analog drift/noise below code quantization;
internal algorithm/clock and width-dependent phase; conversion and inter-bit
details below the **40 ns** observation resolution. No analog thermal model
or per-bit sub-tick sequence is claimed.

## Observation and schedule

Everything uses the board's 25 MHz clock: one tick is 40 ns. No PLL is needed
for the approximately 70 microsecond question. STARTPULSE is a registered
output to DTR. Every DTROUT bit has two retained synchronizer flops, `meta`
then `synced`. No logic consumes the asynchronous bus directly.

Tick zero is the first operational observer edge after configuration; there
is no reset, lock wait, or warmup before sampling. `meta` acquires the bus on
that edge. At tick 2 the recorder reads the old `synced`, containing that
first acquisition, and retains it as I and sample 0 of the baseline. This
avoids reporting the synchronizer's initialized zeros as the initial code.
The first sample can still be metastable; a first-clock reading is not a
guarantee that the sensor was already stable. The first-clock event cannot
describe output activity earlier in configuration or before user registers
become operational.

A complete measurement window is stored as consecutive bytes in a 32768-byte
RAM, mapped to 16 DP16KD blocks. The startup window has a separate immutable
8192-byte RAM (four more DP16KD blocks), filled only at startup. Its original
first-clock value and full-sample checksum are also retained in registers.
Later measurements cannot overwrite startup data. It records every tick,
including all intermediate values;
there is no bounded transition FIFO. Once capture ends, it scans RAM and
transmits only changed values. The maximum window is 23517 samples, leaving
space even if the bus changes every tick. UART transmission cannot drop a
captured change or perturb an in-progress window. Activity outside windows
is not recorded. A pathological every-tick-changing bus makes serialization
slow; timestamps and the observed drift span reveal that slowdown.

For pulse windows, the first rising edge is at sample offset `0x0010` (16).
Sample 16 reads the synchronized value immediately **before** that edge's
registered STARTPULSE update. Rising offsets are `16 + j*gap`, and falling
offsets are `rise + width`. Windows include both sample 0 and the last index.

| Kind | Purpose | Width, ticks | Rise spacing, ticks | Pulses | Last index |
|---|---|---:|---:|---:|---:|
| 0 | Before any STARTPULSE | 0 | 0 | 0 | 7500 |
| 1 | 40 ns pulse | 1 | 0 | 1 | 7516 |
| 2 | 400 ns pulse | 10 | 0 | 1 | 7516 |
| 3 | 100 microseconds high | 2500 | 0 | 1 | 10016 |
| 4 | 600 microseconds held high | 15000 | 0 | 1 | 22516 |
| 5 | Two starts 10 microseconds apart | 1 | 250 | 2 | 7766 |
| 6 | Two starts 30 microseconds apart | 1 | 750 | 2 | 8266 |
| 7 | Two starts 60 microseconds apart | 1 | 1500 | 2 | 9016 |
| 8 | Eight starts 20 microseconds apart | 1 | 500 | 8 | 23516 |
| 9 | Drift readings | 1 | 0 | 1 | 7516 |

The default captures kind 0 once, kinds 1 through 8 for 16 rounds, then 601
kind-9 windows at at least 100 ms between starts. The first-to-last drift
reading spans at least 60 seconds. Afterward it keeps STARTPULSE low and
periodically replays the retained startup group followed by Z.
Every pulse has at least 300 microseconds of following capture; kinds 3 and
4 also retain 300 microseconds after the falling edge. Kind 8 retains 800
microseconds after the last rise, enough for eight nominal 70 microsecond
queued conversions. The held-high case spans several nominal conversions
without presuming that holding high actually repeats conversion.

The startup window is buffered immediately. UART output begins no earlier
than tick 25,000,000 (one second), and repeats the complete startup group
every 12,500,000 ticks (500 ms) while waiting. The first STARTPULSE is gated
until at least tick 75,000,000 (three seconds). A startup report is completed
before proceeding, so the first pulse normally occurs a few milliseconds
after three seconds. An unusually busy startup bus can delay serialization
and therefore delay that first pulse; it cannot make the pulse early.

Each startup replay is I, B(kind 0, sequence 0), all original startup C
records, then E. Replays use the original sample timestamp, codes and
checksum. During the experiment another complete startup group precedes
each subsequent measurement window, with no UART output during capture.
After completion the startup group and Z repeat every 500 ms. A reader
that starts two seconds late can recover the first-clock sample and entire
startup window without receiving any earlier bytes. A reader attaching
even later still recovers startup, but measurements already sent are not
replayed and the analyser reports that missing history.

Later windows start after the preceding measurement report and startup
replay; there is no fixed sweep cadence. For drift, a countdown runs through
capture, transmission and replay; the next window starts when all are
finished. The timestamp records actual time, including slow reports.

Generator options: `--rounds` (default 16), `--readings` (601),
`--period-cycles` (2500000), `--uart-delay-cycles` (25000000),
`--first-start-cycles` (75000000), and `--replay-cycles` (12500000).
Reduced settings are useful for simulation and do not constitute a minute
of drift observations.

## UART format

L4 is `ftdi_rxd`, 115200 baud, 8N1, idle high. The actual divider is 217,
giving 115207.37 baud. Every record begins `Y4` plus its tag; all payload
fields are fixed-width uppercase hexadecimal, most significant digit first,
with no spaces. Every line ends CR LF. The spaces below are explanatory.

```text
Y4I VV TTTTTTTTTTTT SSSSSSSS
Y4B SSSSSSSS K TTTTTTTTTTTT NNNN WWWW GGGG PP VV
Y4C SSSSSSSS OOOO VV
Y4E SSSSSSSS CCCC HHHHHHHH VV
Y4Z SSSSSSSS TTTTTTTTTTTT
```

- I: retained first-clock acquisition VV, observer tick T when this I packet
  was queued, and progress sequence S. S is 0 during the initial wait, the
  upcoming measurement sequence (1 onward) during the experiment, and the
  next unused sequence after completion. I repeats; it does not start a new
  run by itself. T is transmission metadata, not a new sensor acquisition.
- B: sequence S, kind K, absolute 48-bit observer tick T of sample 0,
  inclusive last sample index N, pulse width W, rise spacing G, pulse count P,
  and synchronized code VV at sample 0. Each pulse's exact edges follow the
  schedule above. Kind 0 has no pulse, sequence 0, and begins at absolute tick
  2 on every replay. Measurement B records start at sequence 1.
- C: sequence S, sample offset O of a change, and new full eight-bit value VV.
  Every change after sample 0 is sent, in increasing offset order. There is
  no conversion to signed or Celsius units.
- E: sequence S, number C of C records, unsigned 32-bit sum H of **all**
  `N+1` raw buffered sample bytes, and the final sample value VV. The analyser
  reconstructs constant runs to verify this sum and checks counts and sequence.
  This is an integrity check, not a cryptographic checksum or collision-free CRC.
- Z: next unused sequence number and current absolute tick; experiment complete.
  It repeats after each post-completion startup group; no new conversion runs.

Lines are 27, 42, 19, 27 and 25 bytes respectively, including CR LF. This
extended I replaces the earlier two-digit-only I format; use the updated
analyser. Timestamps do not wrap for about 130 days at 25 MHz.

Within a boot, I transmission ticks increase and progress never decreases.
The analyser uses a reset/decrease of these fields to distinguish a reload
from replay. They are not a globally unique boot identifier: two independently
trimmed captures with coincidentally increasing time/progress cannot always
be distinguished when concatenated. Keep those captures separate. Ordinary
consecutive loads restart progress at 0 and are separated automatically.

For an asynchronous transition seen in sample k, the first-stage acquisition
was on edge k-2; absent extra metastability delay, the physical transition
occurred in `(k-3, k-2]` observer ticks. Raw latency is `change_offset - rise`.
Subtract 2.5 ticks for an estimated physical latency, with nominal +/-0.5
tick sampling uncertainty. STARTPULSE clock-to-output delay, routing,
inter-bit skew and metastability add uncertainty. This is not a coherent
bus handshake. Bits arriving on different observer ticks must be retained
as evidence of asynchronous bus updates; a single observed jump does not
prove synchronous operation. Transitions shorter than one tick can be missed.

## Analysis

```sh
TEST="~/IDE Workspaces/RustroverProjects/ecp5_emu/docs/inventory/LFE5U-85F/hy04_dtr"
PYTHONDONTWRITEBYTECODE=1 python3 "$TEST/hy04_analyse.py" --selftest
PYTHONDONTWRITEBYTECODE=1 python3 "$TEST/hy04_simtest.py"
python3 "$TEST/hy04_analyse.py" /tmp/hy04-capture.txt
python3 "$TEST/hy04_analyse.py" /tmp/hy04-capture.txt --json > /tmp/hy04-analysis.json
```

The default text report gives the first-clock code, baseline changes, first-change
and last-change latency min/max/median by pulse width, no-change counts,
single jumps, multi-step windows, code histograms, spread and drift. JSON
also preserves every change and its offset from **each** applicable pulse,
including overlapping 300 microsecond windows during retrigger tests. It
includes changed-bit masks, multi-tick bus-step clusters, and an explicit
`asynchronous_to_observer_evidence` flag for those clusters.

Adjacent changes no more than `--settle-gap` ticks apart (default 4, 160 ns)
form a cluster. Several changes within a cluster retain possible bit skew
or intermediate bus codes; several separated clusters can be intermediate
conversion codes, repeated conversions, or other activity. Inspect the
raw records and vary the clustering threshold before interpreting them.
The first-change latency is not automatically a conversion-complete latency;
the final-change latency of the held-high case can include repeated updates.

The retrigger analysis calibrates a typical service time from isolated
one-cycle pulses with exactly one visible change cluster. For each close
pulse train it predicts completion times for restart-on-busy, ignore-on-busy,
and serialized queue models, then reports compatible candidates. The
tolerance is at least 8 ticks and expands with the calibration's observed
range. Observed clusters must match distinct predicted events in order;
predicted events may remain invisible when the resulting code is unchanged.
No visible changes leaves all models ambiguous. An early event can rule out
restart; an additional event after the first can support queue; a lone
event after the last trigger can support restart. No matching model is
reported explicitly rather than forced into one category. The assumptions
include a reasonably stable conversion time and one completion cluster;
large jitter or genuine intermediate codes can invalidate that comparison.

Distribution and drift use one **final-window code** per isolated window,
including unchanged readings, rather than counting intermediate codes as
independent conversions. Drift is reported separately for kind 9, with
actual elapsed time, intervals, code range, median, mean, population standard
deviation, histogram, least-squares code/minute slope, and first/last decile
means. These are proxies for conversion results: an unchanged code cannot
prove a conversion ran. No control of temperature is available; room
temperature, board warming, quantization and noise remain confounded.
No degrees Celsius, thermal calibration, or analog emulator model follows
from this run.

The parser discards leading fragments and records until the first complete
I, validates its startup group, then deduplicates every identical startup
replay. Replays never add conversions or reset drift history. A changed
initial value or startup replay within a boot is an error. Repeated Z is
accepted. Lost/reordered measurement windows, malformed records after initial
synchronization, bad counts, checksums and final values are rejected. Missing
Z or an unfinished final window is reported as incomplete. If the first I
progress is greater than 1, the report identifies missed measurement sequences;
`device_done` can be true while `complete` remains false for that late capture.

## Emulator check

`src/compile/dtr.rs` dispatches `DTR.MODE`: DTR instantiates the event block,
NONE has inactive X outputs. `compile::Board::dtr_code` is the environment's
full byte (including bit 7); `None` uses the measured room-temperature ULX3S
0x9E. It lives beside `oscillator_hz` in `src/compile/mod.rs`, so no change to
`src/board.rs` is needed. A caller can supply `Board { dtr_code: Some(0xA1),
..Board::default() }`; this is a byte profile, not a temperature in Celsius.

Before any pulse, all DTROUT bits hold that code. Assertion clears the whole
bus to 00 and cancels pending completion. A definite high-to-low transition
schedules the profile byte exactly 32.740 us later. Until then all eight bits
stay zero, including bit 7 (done). Holding high never completes. Retrigger
cancels/restarts rather than queues. X/Z controls cancel work and hold 00
until a known high then low starts conversion. Initial high holds 00 until
its fall; initial low holds the profile without an invented edge. These
unmeasured input cases are explicit two-valued policies. Active DTR never
emits X; MODE NONE remains inactive X.

The completion timer has a generation tag, preventing an abandoned conversion
from restoring a stale code. The profile participates in plan-cache identity;
DTR controllers bypass the plain-kernel snapshot cache, whose schema version
also changes for the new signal-consumer list.

Fast mode now executes this profile (`1c79418`). When captured STARTPULSE
changes, the generated program returns 2 to pause for the host. The host clears
DTROUT, cancels the old deadline, and on a definite fall schedules the profile
byte at exactly **fall + 32 740 000 ps**, then resumes execution. Completion
and any coincident clock edge enter the same input batch before captures, so
a register on that edge reads the completed byte. A new assertion cancels and
restarts the conversion; holding high never completes. Fast run snapshots
retain DTR control history and the pending deadline. DTR designs use the
host-aware schedule; programs without DTR remain byte-identical. The plain
event-kernel snapshot-cache exclusion above is a different mechanism. Fast
mode still requires binary STARTPULSE; the event kernel supplies the X/Z policy.
